## Overview

This dashboard is for a prospective homebuyer or their advisor comparing registered under-construction projects in Gujarat. The decision it improves: which projects to shortlist and ultimately book, judged on the promoters' own statutory filings rather than marketing claims, with every finding traceable to its source record.

The current dashboard shows one project at a time: a header dropdown selects one of 9 projects and the eight tabs (dossier, pricing, delivery-forecast curves, claim fact-checker, discrepancy audit, knowledge graph, document vault, document search) describe it. A user cannot ask "which projects in Gandhinagar finish by 2028 and cost less than their neighbors," cannot compare projects side by side, and cannot question a set of projects at once. This concept adds a search-first **Explore** entry point, a **Shortlist & Compare** view, and **Ask Across Projects** scoping for the copilot, keeping the existing per-project workbench as Project Detail.

Anchored hypothesis (confirmed by the author 2026-11-11 before review): ship the first release on the current Python-served stack — a filterable, sortable Explore table over the 9-project curated database, the two validated summaries (filing freshness, completion-revision status in three honest states), Project Detail with match-reason and evidence links, and a localStorage shortlist with a basic side-by-side of shortlisted projects. Local price benchmark, architect-filter hardening, related-case tier-2/3 views, the benchmark column in Compare, and cross-project Ask follow in later stages gated on verified data coverage. The statewide 17,634-project index stays out until its download gaps are audited (author decision 2026-11-11).

## Analysis

Six lenses reviewed the pre-review draft (`concepts_brief-2026-11-11-pre-review.md`): design (Hostile Design Critic), codebase-details (Pedantic Technical Auditor), zoom-out (Skeptical Architect/YAGNI), comprehension (Naive Reader), implementation-readiness (Pragmatic Tech Lead), structural (Document Architect). Every re-checkable data claim was re-verified against the database by two lenses independently. Findings below are deduplicated; severity is the highest assigned by any lens.

### Findings confirmed correct (kept)

The data-gating discipline, evidence-first framing, no-migration call, cutoff-date printing, "not stated, never zero" rule, absence-of-records-is-not-absence-of-cases rule, localStorage shortlist (~10 lines, in-repo precedent `copilot_api_key`), URL-hash state as migration insurance, and the statewide deferral were all endorsed. Scenario 1's "5 of 9 qualify" is exact; filing freshness genuinely discriminates (latest filings span 2025-12-16 → 2026-10-07).

### Blockers

1. **Explore's data source does not exist.** `/api/projects` returns exactly `project_id, name, district, promoter_name` (`server.py:1682`) — no registration number, taluka, completion date, stage, complaints, filing dates, price aggregates, or revision flags. Client-side *filtering* was confused with client-side *data*; a new data endpoint is unavoidable even with client-side logic. **Resolution adopted:** add `GET /api/explore` returning one pre-aggregated row per project (`{project_id, name, registration_number, district, taluka, project_type, promoter_name, completion_date, progress_pct, complaints_count, extensions_count, latest_filing_date, filings_count, unit_types[], min_price_booked, min_rate_sqft_booked, price_date_min, price_date_max, revision_state, architects[]}`, explicit nulls, 400 on malformed params), contract defined in this brief before implementation and added to the `ui/EGM.md` route table in the same commit. Filtering/sorting stays client-side at 9 rows. Do not route Explore through `/api/pricing/{pid}` (BOOKED-only aggregates, per-project) or the MCP analytics routes (lazily trained models).
2. **The pre-review draft misstated the graph evidence.** `graph_edges` contains DESIGNED_BY (8), DEVELOPED_BY (9), ENGINEERED_BY (8), ESCROW_AT (9), PRIOR_PORTFOLIO (18) — **zero `PROBABLE_SAME_AS` edges exist** (that mechanism is aspirational in `docs/SPEC.md`, never implemented), and professional edges are keyed by normalized name only, not verified license numbers (architect rows: 8/8 missing license numbers). Tier-3 related-case views as drafted are vacuous on current data. Related bug found: `graph/network.py:87-93` does not exclude self-links, so the graph duplicates each project as its own prior-project node (the dossier endpoint correctly excludes them since the 2026-11-09 fix), and `promoters.linked_gujrera_projects_count` counts the self-link. **Resolution adopted:** tier-3 is relabeled name-equality professional sharing; the UI states "no soft entity links exist in this database" until that mechanism is actually built; the graph self-link exclusion is added to the fix list.
3. **The pre-review draft contradicted itself on release scope.** It deferred "side-by-side comparison" in the hypothesis while shipping "a basic side-by-side" in the first release; "the supported filters" was undecidable (partial-marked filters in or out?); and acceptance scenario 1 required cross-project Ask, which release 1 defers. **Resolution adopted:** the explicit Goals vs. Non-Goals section below now owns the scope boundary; scenario 1's question ("which of these revised their completion dates?") is answered by the Compare grid's revision-status column — deterministic, zero hallucination risk — and the Ask step is gated to the follow-on stage; shipped filters are named exhaustively in Goals.
4. **38% of "recorded transaction prices" are not recorded transactions.** `unit_transactions.status`: 1,037 BOOKED / **636 UNBOOKED**, both carrying fully populated rates — UNBOOKED rows are declared inventory prices, exactly the class the concept says must never mix into price columns. The existing `PricingIntelligence.get_project_pricing_summary` already restricts rate statistics to `status = 'BOOKED'` (`analytics/pricing.py:88-91`). **Resolution adopted:** Explore's price columns, aggregates, and any benchmark use BOOKED rows only, matching the platform's own established pattern; the endpoint field names carry the `_booked` suffix and the UI labels the basis ("lowest registered agreement price").
5. **The fixture mechanism had no implementation seam.** There is no `locality` column on `projects`, no demo/fixture flag in `start_server`, no fixture/live ID separation (shared integer ID space — a shortlist built during a fixture walkthrough would silently bind to unrelated live projects), and no banner signal. Two lens-compatible options exist: **(a)** defer fixtures entirely — validate scenario 2's interaction design with a static annotated mock (screenshots in `docs/reviews/ui-discovery/`), re-run live when locality data lands (the feature gate and the demo gate become the same gate) — or **(b)** build a separate `intelligence_demo.sqlite` via a committed script (live 9 rows copied + fixture rows with `data_scope='fixture'`), requiring a `projects.locality` + `data_scope` schema migration with `db/EGM.md` update, served via the existing `serve --db` flag, with namespaced shortlist keys. **Author decision requested; recommendation: (a) for release 1** — option (b) is scaffolding for features that remain data-gated, and the migration it requires belongs to the benchmark stage where a locality column lands for real data anyway.

### Major findings

- **Thread-safety of the new server is real but the justification recorded is wrong, and there is a lazy-init race.** `KnowledgeGraph.__init__` executes DDL and `commit()` on the shared connection (a write), safety actually comes from SQLite's serialized threading mode on the single shared connection (`check_same_thread=False`), not WAL; and `RealEstateIntelligenceMCP` lazily trains the hedonic and survival models under an unguarded `if self._pricing_model is None` (`mcp/server.py:232-234, 268-272`) — two concurrent analytics requests will both train, wasting seconds of CPU. **Fix list additions:** train both models eagerly in `setup_backends` (or guard with a `threading.Lock`), and correct the `ui/EGM.md` invariant wording.
- **Copilot render pipeline injects HTML and its citations are decorative.** `formatBotReply` converts markdown to HTML without escaping first; citations and FTS snippets interpolate into `innerHTML` raw; the deterministic copilot's citations are labels like "RERA Act 2016 Buyer Protection Guidelines" with no run/form/SHA token — short of the platform's own Evidentiary Citation Contract (`docs/SPEC.md` Implementation Decision 11). The deterministic router also silently substitutes the lowest project ID when `project_id <= 0` — a trap for cross-project Ask. **Resolution:** escape-then-markdown in this release (fix list); deep-link evidence built on real row addressing is scoped to the two Explore summaries where records are addressable; copilot evidence claims stay out until citations carry structured tokens; the substitution fallback is removed at the Ask stage, and release 1 shows an explicit project binding when the copilot is opened from Explore (no silent default).
- **Unit-scoped filter semantics were undefined.** A row is a project, but unit-type, carpet-range, price-window and price-bound filters match against units. **Resolution adopted — cascade:** (i) unit-scoped filters (unit type, carpet min/max, agreement-date window) restrict each project's unit set; (ii) aggregates (lowest price, lowest ₹/sq ft) compute over the restricted BOOKED set; (iii) price min/max filters test those aggregates; (iv) a project matches only if its restricted set is non-empty and aggregates satisfy the bounds. Chip labels state the semantics ("lowest price ≤ ₹X").
- **Specification gaps an implementer would have to improvise (implementation-readiness verdict: NOT READY as drafted).** Sort (default district asc → name asc, tiebreak project_id, nulls last; sortable columns: name, district, completion date, progress %, lowest price, lowest ₹/sq ft, freshness days). State schema (`{q, filters{}, sort{col,dir}}` serialized as a URL-encoded querystring in the hash; hash wins on load; sessionStorage `gujrera.exploreState.v1` refreshes it; drop "page" — no pagination at 9 rows). Test plan: `test_api_explore_shape_and_fields`, `test_api_explore_empty_db`, `test_revision_state_three_states`, `test_freshness_computation`, `test_explore_price_columns_booked_only`. Rollout sequence: commit the verified fix pass first, then feature commits in order — (1) `/api/explore` + `ui/EGM.md` + tests, (2) Explore template, (3) summaries, (4) shortlist + Compare-lite, (5) demo artifacts if option (b) is chosen.
- **Simplicity cuts at n=9 (zoom-out lens, endorsed by the discriminating-power data).** Filters that actually narrow: completion window (9→5), freshness (9→6), revision status (9→2), complaints (9→4), architect name (9→1–2), price/₹-sq ft ranges, unit type. District/taluka are near no-ops (9→8; taluka co-terminous with district). **Release-1 rail:** search + completion-on-or-before + max price / max ₹/sq ft + unit type + district + min construction stage + has-complaints/has-extensions — everything else is a sortable column. Removed from release 1: removable filter chips (controls already show state), per-filter unknown-value counters (one aggregate "not stated" line instead), sessionStorage duplication of the hash, summary-badge-click-applies-filter (summaries become sortable columns), freshness buckets with quarterly re-anchoring (a date + days-ago column with the printed computation date carries the same honesty at zero maintenance), and the value-for-money checklist (deferred with the benchmark it depends on).
- **Application-date quality and provenance.** 62% of `applications.apply_date` values are unusable (28 NULL, 23 Excel-serial numbers like "190130"; only 31/82 parse), and the two Extension timestamps may be portal fetch times rather than filing dates. **Resolution:** revision status reads `applications` (the row is the evidence; `projects.has_extensions` is the derived display flag), renders unparseable dates as "date not disclosed", and never presents the timestamp as a verified filing date. Tier-2 (promoter join) is empty on today's data (no promoter_id shared by two curated projects) — the matrix says so; the real cross-project link today is one shared architect (name-equality, projects 16104/16562), and promoter history lives in `previous_projects` (18 rows, 9 self-links, linked IDs outside the curated 9 with no application data).
- **Benchmark gate restated (was internally inconsistent: ≥2 vs ≥3, "degraded form" undefined).** The benchmark ships only when a comparison group — same district + project type + **unit type** (stratification is mandatory; an unstratified Mixed-Development median mixes ₹2,755 shops with ₹17,904 residential rates) — contains ≥3 projects with ≥5 BOOKED transactions each within the active 24-month window, with the construction-stage caveat printed alongside and the group composition (n projects, n transactions, date window) shown whenever a benchmark renders. The "insufficient comparable data" state is expected to be the common case initially; that is the gate working. "Lowest ₹/sq ft" computes within the active price window; with no window set it prints the winning unit's agreement date and warns that 2022 and 2026 prices are not directly comparable.
- **Offline-first contradiction and the template bottleneck.** Tailwind loads via the unversioned Play CDN (a runtime compiler documented as non-production), vis-network is unpinned (upstream major bumps reach the browser silently), Font Awesome 6.4.0 and Chart.js 4.4.4 are pinned; offline, the UI is unstyled and chartless, contradicting the SPEC's sovereign local-first claim. The 1,625-line HTML/JS block inside a Python string is the maintenance bottleneck and pushes past ~3,000 lines with release 1. **Resolution:** an intermediate refactor before any framework talk — move HTML/CSS/JS into static files served by the same stdlib server with pinned, vendored assets (amends the `ui/EGM.md` "no static files" invariant). **Author decision requested** (pairs with the standing CDN question).
- **Comprehension debts (naive-reader lens, 24 findings — the load-bearing ones).** "index + latest" filings never defined (they are capture artifacts of one run, not evidence a promoter filed only twice — must be stated); BCR / LEGAL_PCWF / TP_PCWF defined nowhere including the glossary; "filing freshness" never connected to QPR (the brief said "filing" without naming the quarterly progress report); Form 3 described in a way irreconcilable with the glossary's CA-certificate definition (prices come from the booking records attached to it); complaint-vs-order distinction asserted but unexplained; the three revision states defined mechanically but never in buyer terms, and "revision observed" overstates — an extension application is not necessarily approved (`application_status` is null on all rows), so the buyer-facing wording is "the promoter has formally applied to extend the completion date (filed X); whether it was approved is not disclosed"; the 9-project provenance unexplained; glossary linked once in the whole document. **Resolution:** the buyer-terms rewrites and glossary links are incorporated in this revision; BCR/PCWF definitions to be sourced from the pipeline catalog before RFC (flagged).
- **Structural reformation (structural lens).** The pre-review draft had 12 top-level sections where the EGM template mandates 5, no Goals vs. Non-Goals, zero H3 headings, self-contradicting Open Questions, duplicate author decisions, and had already drifted from `UI_COMPONENT_PLAN.md` on scenario 2 and the benchmark threshold. **Resolution:** this revision adopts the template structure; `UI_COMPONENT_PLAN.md` is reduced to pointers for concept content (plan owns executed state only).

### Minor findings (recorded, incorporated where trivial)

`/api/search` and analytics endpoints parse `int()` unguarded (connection-drop instead of 400) and the copilot catch-all returns raw exception text — guarded-parse helper + sanitized error (fix list); no concurrency cap on `/api/copilot` (semaphore proposed); `json.dumps` can emit `NaN` breaking `res.json()` once benchmark code computes over empty groups (`allow_nan=False`); `filing_date` ISO offsets lack colons (tolerant parsing); hash/sessionStorage precedence rule (hash wins); document the localStorage API-key fact; engineers also lack `firm_name` 8/8; `rate_per_sqft` derives in `db/reader.py:194` (attribution corrected); server emits `days_since_latest_filing` server-side in UTC so the cutoff is not browser-clock-dependent; "sanitized fixtures" renamed "labeled demo dataset" (synthetic data is not "sanitized"); the tab name "ML curves" is really the delivery-forecast tab; architect name-match chips get a "(name match only)" suffix; price columns carry a one-line basis note ("recorded agreement consideration; may differ from cash paid").

## Goals vs. Non-Goals

* **In-Scope Goals (release 1):**
  * `/api/explore` aggregate endpoint (contract in Blocker 1) + `ui/EGM.md` route-table entry + tests.
  * Explore table: free-text search (name, promoter, registration number); filters — completion-on-or-before date, max total price, max ₹/sq ft (BOOKED), unit type, district, min construction stage %, has-complaints, has-extensions; sortable columns (name, district, completion date, progress %, lowest price, lowest ₹/sq ft, freshness); "N of 9 match" counter; one aggregate "not stated" line for missing values; URL-hash state (`{q, filters{}, sort{col,dir}}`).
  * Two summaries as sortable columns with printed computation dates: filing freshness (date + days-since-latest-filing, server-computed) and completion-revision status in three states (*date moved — extension application filed, approval not disclosed* / *no move on record* / *not enough history*).
  * Project Detail: existing 8 tabs unchanged post-fix, plus a match-reason strip (hit filters highlighted) and evidence deep links for the two summaries (filing pair, extension row).
  * localStorage shortlist (`gujrera.shortlist.v1`) + basic side-by-side of shortlisted projects using Explore's definitions (total price and ₹/sq ft as separate rows with dates; gaps as "not stated").
  * Copilot: single-project scope unchanged, project binding shown explicitly when opened from Explore.
  * Fix-list additions from this review: eager model training in `setup_backends`, copilot escape-then-markdown, graph self-link exclusion, guarded query-param parsing, sanitized copilot errors.
* **Out-of-Scope Non-Goals (release 1):** local price benchmark (gate restated in Analysis); architect filter beyond a sortable column (name-equality hardening later); related-case tier-2/3 views; the benchmark column in Compare; cross-project Ask (Compare grid answers scenario 1's question deterministically); statewide ingestion (deferred pending download-gap audit); frontend migration; server-side filtering; `market_listings` activation; fixture/demo data in the live server (static mock for the scenario-2 walkthrough unless the author opts for the demo-DB design).

## Alternatives Weighed

- **Vue + Vite + shadcn-vue or React + Vite + shadcn/ui migration now** — rejected for release 1 by the review (all six lenses compatible with this): at 9 rows the template patterns suffice; migration costs 6–9 days of parity work before any new feature. Component mapping completed in `docs/UI_COMPONENT_PLAN.md` §5–§6; migration deferred behind two named triggers (statewide ingestion → TanStack Table pays off; the Ask stage → the only official copilot catalog, AI Elements, is React-only and folds into shadcn/ui end of Nov 2026). New intermediate step adopted from review: extract the template to static files and vendor pinned assets before any framework decision.
- **Server-side filter API from day one** — rejected; client-side filtering at 9 rows. The distinction the review forced: filtering client-side ≠ data client-side — the `/api/explore` aggregate endpoint ships in release 1 either way, and its contract is written so the same filter state can later drive a server-side query.
- **Ingesting the statewide 17,634-project index before UI work** — rejected by the author (2026-11-11): the statewide collection is incomplete (pending downloads, missing details). Follow-on: download-gap/coverage audit first, then ingestion, then the Explore filters upgrade to server-side using the unchanged URL-hash state.
- **A blended "value score"** — rejected by the author's brief: lowest price, lowest ₹/sq ft, and vs-benchmark stay separate sorts; a composite would hide trade-offs.
- **Fixture-backed scenario 2 in the live server** — challenged by two lenses (zoom-out: scaffolding for data-gated features; implementation-readiness: seam, schema migration, and ID-space hazards). Alternatives: static annotated mock (recommended) vs separate `intelligence_demo.sqlite` with `data_scope` column (viable, costs a `projects.locality`+`data_scope` migration and a build script). Author decision pending.
- **Freshness buckets (≤35/≤95/>95 days)** — rejected by review as recurring maintenance for 9 dates (magic numbers, quarterly re-anchoring invalidates old screenshots); replaced by date + days-ago column with printed computation date. Buckets may return as a pure display derivation at statewide scale.
